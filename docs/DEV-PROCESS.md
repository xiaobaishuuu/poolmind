# PoolMind 正式开发流程（2026-07-21 用户定案）

> 从「UI demo 设计阶段」进入「正式写代码阶段」后，这份文件是**唯一的团队协作与审核门规则**。
> 每次开始写代码前先读本文件；规则本身变了才改。技术选型/里程碑请看 `.omc/plans/poolmind-phase1-plan.md`，业务需求请看 `docs/SPEC.md`。

## 1. 固定团队编制（不再临时拼团队）

以前每次做任务都临时组一次团队（`/team` 现场拉人）。**从正式开发阶段起改为固定编制**：同一个角色永远对应同一种专家，主 agent（我）永远按下表分派，不再每次现场决定"这次找谁"。

| 角色 | 对应专家（Agent 类型） | 负责什么 | 什么时候用 |
|------|------------------------|----------|------------|
| **项目经理（PM）** | 主 agent（我本人，一直在场） | 拆功能单元、分派任务、把关审核门、维护文档、向你汇报 | 全程 |
| **后端开发** | `oh-my-claudecode:executor`（opus 模型） | 写 API、数据库、状态机、定时任务等服务器代码 | 每个后端功能单元 |
| **前端开发** | `oh-my-claudecode:executor`（opus，接后端逻辑用）/ `oh-my-claudecode:designer`（新增/调整界面用） | 把 demo 页面接上真实数据和逻辑，或做全新界面 | 每个前端功能单元 |
| **测试工程师** | `oh-my-claudecode:test-engineer` | 写自动化测试（单元/集成/端到端），跑测试 | 每个功能单元完成后，审核门之前 |
| **代码审查** | `oh-my-claudecode:code-reviewer`（一般功能）/ `oh-my-claudecode:security-reviewer`（涉及登录、证件、工资、支付、个人隐私时） | 挑毛病、找漏洞，绝不由写代码的那个专家自己审自己 | 每个功能单元完成后，审核门之前 |
| **除错** | `oh-my-claudecode:debugger` | 遇到 bug、报错、测试跑不过时定位根因 | 出问题时按需 |
| **Git 管理** | `oh-my-claudecode:git-master` | 整理提交记录、写 commit message | 只在你明确同意要 commit 时才用 |

**你不需要记住这些角色叫什么**——你只需要知道：每完成一件事，都有一个"写"的人和一个"另外挑毛病"的人，两个身份不会是同一次调用，这是防止我自己写完自己说"没问题"。

## 2. 功能单元怎么切（颗粒度）

以前的规则是"每个 §13 验收条目/功能块"停一次，这次你要求更细：

> **前端算一个单元，后端算一个单元，其他（数据库/部署/测试/文档等）也各算一个单元。做完一个，就停下来找你审。**

举例：「救生员注册」这一个 SPEC 功能，正式开发时会拆成好几个独立审核点，不会一次性全做完才给你看：

1. 数据库表设计（User / Certificate 等）——**其他类单元**
2. 注册 API（用户名查重、密码、OCR 对接、WhatsApp 验证 webhook）——**后端单元**
3. 注册页面接上真实 API（把 demo 的 L1 三步页面从"假数据"换成"真的会存进数据库"）——**前端单元**
4. 自动化测试（注册流程的单元测试+集成测试）——**其他类单元**

每一个都单独停下来给你看，而不是等整个"注册功能"都做完才一次性汇报。这就是你说的"逐个功能精雕细琢"。

## 3. 一个功能单元的标准流程

```
1. PM 用业务语言告诉你："接下来要做 X（前端/后端/其他），大概做什么、为什么"
   → 你可以在这一步就叫停或改方向
2. PM 分派给对应专家实现，专家自己先做基本自测（能跑、无报错）
3. 测试工程师补自动化测试（如适用）
4. PM 另外叫一个审查专家挑毛病（code-reviewer 或 security-reviewer）
   → 发现问题打回第 2 步重做，不给你看半成品
5. PM 停下来，用业务语言＋可核验的证据向你演示：
   - 前端：截图或告诉你打开哪个文件/哪个网址，你自己点一下
   - 后端：告诉你测试跑的结果（通过几条/失败几条），或一个可以实际调用的示例
   - 其他：给你看变化前后的对比或结果
6. 你审核 → 通过才继续；不通过就按你的反馈改，回到第 2 步
7. 通过后：PM 补一份 `docs/dev-log/YYYY-MM-DD-<功能名>.md`（发生了什么、为什么这样做），
   更新 `docs/PROGRESS.md`，问你是否要 git commit（除非你已经把这一条设成"自动 commit"）
8. 进入下一个功能单元，回到第 1 步
```

**核心原则：没有你的明确通过，PM 不会自己往下走到下一个单元。** 这条对所有功能单元一视同仁，不因为"这个我觉得很简单"就跳过审核门。

## 4. 演示怎么给（因为你不是程序员）

- 前端类：优先给可以直接双击打开/点击操作的页面，或明确的截图；不讲代码术语，讲"这个按钮按下去会发生什么"。
- 后端类：没有界面可看，所以用"测试结果 + 一句人话总结"代替，例如："写了 12 条测试，全部通过，测的是：用户名重复会被拒绝、密码太短会被拒绝、验证码对了才能注册……"
- 涉及钱（工资/支付）或身份证件的功能单元，一律标注「⚠ 高风险单元」，审查环节强制用 `security-reviewer`，且演示时额外说明"万一算错/泄露会怎样、这次怎么防的"。

## 5. 注释与代码标记规则（沿用既有约定，此处仅索引）

- 每个函数/代码块中文注释，注明业务对应哪条 SPEC 规则（详见 `.omc/plans/poolmind-phase1-plan.md` "执行方式约束"）。
- 测试壳/临时代码标记：`【壳-待补】`、`【长期测试】`、`【临时测试-用完即删】`（详见 `docs/design/DEMO-RULES.md` §5，正式代码沿用同一套标记）。

## 6. 代码组织与环境隔离（2026-07-21 用户定案）

- **代码按业务模块分类，不准全部堆一起**：后端 `apps/api/src/modules/` 下每个业务域一个独立目录（auth、certificates、venues-pools、recruitment、chat、roster、payroll、notifications、audit、admin-tools…，对齐 `.omc/plans/poolmind-phase1-plan.md` 的数据模型实体）；前端 `apps/web/src/` 按角色页面（supervisor/lifeguard/admin）+ 跨端共享组件分。改哪个业务就进哪个目录改，不必整仓库翻。
- **改动留痕精确到函数级**：见 `docs/dev-log/README.md` 规则 2——每次改完代码，dev-log 里必须列出改了哪个模块/哪个文件/哪几个函数，不能只写"改了 XX 功能"。
- **测试库与正式库物理隔离，绝不共用**：开发库（`poolmind_dev`，本地手动跑代码用，数据会保留）、测试库（`poolmind_test`，自动化测试专用，每次跑测试前清空重建，跑坏了也没关系）、正式库（生产环境 RDS，独立密钥，本地代码连不上）三者分离，连接字符串各自走 `.env.development` / `.env.test` / `.env.production`（生产文件不进 git，只留 `.env.example`）。
- **WhatsApp 验证（Spike/M0 阶段的真实实现，非 demo 壳）**：Meta 商业验证批下来前，先做"管理员人工核号"路径（计划里本来就设计好的 break-glass 备选方案，现在提前当主要实现用）——注册流程走到验证手机号这步，系统生成验证码给用户看（和最终产品体验一致：用户被要求把这段码用自己 WhatsApp 发去平台号码）；因为入站 webhook 还没接通，改用一个后台管理工具，人工输入"手机号+验证码"来模拟 webhook 收到匹配消息、标记已验证。核心校验逻辑写成独立函数，将来 webhook 接通后调用同一个函数，人工核号继续留作备用通道。
- **OCR 维持壳**：证件照任意上传即通过，不接驳真实 OCR 服务，正式接入等用户通知（同 `docs/design/DEMO-RULES.md` §5）。
